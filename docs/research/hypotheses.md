# oradump hypotheses (Scout, for the Analyst)

Round 1 and Round 2. Every hypothesis is unverified and comes from claims in
docs/research/sources.md. None of these has been checked against a fixture.

Important framing (C-020): the source material describes the datafile / DUMP() /
OCI byte form. No source says that EXP or Data Pump files store values the same
way. So every type hypothesis below is really two statements: "the datafile form
is as the source says" and "the dump file uses that same form". The Analyst should
test the second. If a fixture disagrees, that is a finding, not a failure of the
hypothesis list.

Format of each entry: ID, statement, how to test, claim IDs.

## NUMBER

H-001
- Statement: The value 123 is encoded as the three bytes 0xC2 0x02 0x18 (decimal 194,2,24).
- Test: put 123 in a NUMBER column, export, find the value bytes in the dump, compare with the truth file.
- Claims: C-002, C-003
- Result: confirmed for legacy EXP 18c, both paths. 123 is `c2 02 18`, preceded by the length `03 00`: t_num_exp_18c.dmp@0x2291, t_num_exp_direct_18c.dmp@0x2283 (truth_num.txt row 8). The dump holds exactly the DUMP(v,16) bytes for all 33 rows of t_num. See docs/formats/exp.md section 6.1. (Analyst session 2) Session 4, Oracle 11g: the same. `03 00 c2 02 18` at t_num_exp_11g.dmp@0x2291 and t_num_exp_direct_11g.dmp@0x2283; all 33 rows equal truth_num.txt of corpus/fixtures/11g on both paths (docs/formats/exp.md section 13.1; the two files are byte-identical to the 18c files from offset 0x2000 on). (Analyst session 4)

H-002

- Claims: C-002, C-004
- Result: confirmed for legacy EXP 18c, both paths. 0 is the single byte `80` (length field `01 00`): t_num_exp_18c.dmp@0x224a, t_num_exp_direct_18c.dmp@0x224a (truth_num.txt row 1). (Analyst session 2) Session 4, Oracle 11g: the same, `01 00 80` at t_num_exp_11g.dmp@0x224a and t_num_exp_direct_11g.dmp@0x224a (truth_num.txt row 1 of corpus/fixtures/11g). (Analyst session 4)

H-005
- Statement: Negative numbers get a trailing 0x66 (102) only when there are fewer than 20 mantissa bytes. A negative number with 20 mantissa bytes has no terminator.
- Test: a negative value with 38 significant digits, and a short negative value.
- Claims: C-002, C-005
- Result: confirmed for the cases in t_num, legacy EXP 18c, both paths. Negative with 20 mantissa bytes, no trailing `66`: `2c 64 4e 38 22 0c ... 22 15` (21 bytes) at t_num_exp_18c.dmp@0x2434, t_num_exp_direct_18c.dmp@0x23f6 (truth_num.txt row 32). Negative with 19 mantissa bytes ends in `66`: t_num_exp_18c.dmp@0x234d (row 22); short negatives end in `66`: @0x225d (row 3), @0x229c (row 9). The dump bytes equal DUMP(v,16) in every case. (Analyst session 2) Session 4, Oracle 11g: the same bytes at the same offsets, t_num_exp_11g.dmp@0x2434 (row 32, no trailing `66`) and @0x234d (row 22, ends in `66`). (Analyst session 4) Session 7: confirmed again with the R-024 values on 18c and 11g: -9223372036854775808 has 11 mantissa bytes and ends in `66` (`35 5c 4f 44 1d 62 21 2f 18 2b 5d 66` at t_num2_exp_18c.dmp@0x22d9 and t_num2_exp_11g.dmp@0x22d9, truth_num2.txt row 12); -99, -100, -1000000, -.001 end in `66` (@0x2281, 0x228c, 0x2257, 0x226c). The byte `66` cannot be a negative digit byte (those are `02` to `65`), so dropping a final `66` is unambiguous; tools/num_decode.py decodes and re-encodes all 72,928 NUMBER fields of the 169 EXP files with this rule. See docs/formats/exp.md section 6.1. (Analyst session 7) Session 9: confirmed again with values computed by SQL: -1/3 is `3f` + 20 x `44`, 20 mantissa bytes and no trailing `66` (t_num3_exp_18c.dmp@0x22c1 and t_num3_exp_11g.dmp@0x22c1, truth_num3.txt row 5). A computed quotient or average gets the full 20 mantissa bytes on both versions (rows 1 to 6, e.g. 1/7 = `c0` + 6 x `0f 1d 3a` + `0f 1e` @0x2287), so negative values without `66` are not rare in computed data. docs/formats/exp.md section 6.1. (Analyst session 9)

(Analyst session 2) Session 4, Oracle 11g: the same, `c0 33` at t_num_exp_11g.dmp@0x22bf, `c0 06` at @0x22c9 (truth_num.txt rows 12, 13 of corpus/fixtures/11g). H-007
- Statement: In a dump file the NUMBER value is preceded by a length that is either the column length alone or a leading byte as in OCI. Whether a separate length field exists is unknown. Check whether it is 1 byte, 2 bytes or something else, and whether the length counts itself.
- Test: look at the bytes immediately before the C2 02 18 sequence for 123.
- Claims: C-001, C-006 (conflict K-3)
- Result: decided for legacy EXP 18c: a separate length field exists. Every value, NUMBER included, is preceded by a 2-byte little-endian length that counts the value bytes only (it does not count itself); there is no further OCI-style length byte inside the value. Bytes before `c2 02 18` (123) are `03 00`: t_num_exp_18c.dmp@0x2291, t_num_exp_direct_18c.dmp@0x2283. The same field is 2 bytes for every length from 1 to 2000 (docs/formats/exp.md section 5.2). The column descriptor of a NUMBER holds 22 as maximum length (t_num_exp_18c.dmp@0x223c), which is not the length of a value. Data Pump not examined. (Analyst session 2) Session 4: the same on Oracle 11g (`03 00` before `c2 02 18` at t_num_exp_11g.dmp@0x2291; descriptor 22 at @0x223c). The 2-byte little-endian length holds for every length up to 3000 (`b8 0b` at corpus/fixtures/11g-cp1251/ru_tbl_exp_cp1251_11g.dmp@0x4727) and is not interrupted at a record boundary: its two bytes can be the last byte of one record and the first of the next (`eb` at t_bn1_exp_18c.dmp@0x3fff, `04` at @0x4000; the same in t_bn1_exp_11g.dmp). See docs/formats/exp.md sections 1.2, 13.7. Data Pump not examined. (Analyst session 4)

## TIMESTAMP family

H-012
- Statement: The first 7 bytes of a plain TIMESTAMP value use the same encoding as DATE (C-007), and the fractional second follows in 4 bytes. For example, TIMESTAMP(9) 2016-03-26 15:09:27.649491000 (this exact value is a guess for the test; do not treat it as from the source) would end in a 4-byte count. The byte order of that count is not stated by C-010. Determine it from a fixture with a fraction like .000000001 (expected 00 00 00 01 if big-endian, 01 00 00 00 if little).
- Test: insert 2016-03-26 16:09:27.000000001 into TIMESTAMP(9).
- Claims: C-009, C-010
- Result: confirmed for legacy EXP 18c, both paths; the fraction is big-endian nanoseconds. TS9 2016-03-26 16:09:27.000000001 is `78 74 03 1a 11 0a 1c 00 00 00 01`: t_ts_exp_18c.dmp@0x22fa (length field; the 4 fraction bytes at 0x2303), t_ts_exp_direct_18c.dmp@0x22f6 (truth_ts.txt row 3). TS6 .000001 ends `00 00 03 e8` = 1000: t_ts_exp_18c.dmp@0x22ed. The first 7 bytes follow the DATE layout. t_ts was not in the fixture list of session 2; checked with tools/check_truth.py (18 fields per path equal DUMP). (Analyst session 2) Session 4, Oracle 11g: the same, `78 74 03 1a 11 0a 1c 00 00 00 01` at t_ts_exp_11g.dmp@0x22fa (truth_ts.txt row 3 of corpus/fixtures/11g); 18 fields per path equal DUMP. (Analyst session 4)

H-013
- Statement: The length of a plain TIMESTAMP value depends on precision and lies between 7 and 11 bytes. Whether the 4 fraction bytes are dropped when the fraction is zero, or when precision is 0, is not stated anywhere and needs a fixture.
- Test: columns TIMESTAMP(0), TIMESTAMP(6), TIMESTAMP(9) with zero and non-zero fractions; compare the lengths.
- Claims: C-009
- Result: decided for legacy EXP 18c, both paths: the length is 7 or 11, nothing in between in these fixtures. The 4 fraction bytes are dropped when the fraction is zero, whatever the declared precision: TS6 and TS9 with .000000 are `07 00` + 7 bytes at t_ts_exp_18c.dmp@0x22cc and @0x22d5 (truth_ts.txt row 2). TIMESTAMP(0) is always 7 bytes (@0x229a, row 1). With a non-zero fraction TS6 and TS9 are both 11 bytes (@0x22a3, @0x22b0, row 1). The column descriptor holds 7 for TIMESTAMP(0) and 11 for TIMESTAMP(6) and (9) (t_ts_exp_18c.dmp@0x2288, 0x228c, 0x2290). Precisions 1 to 5 and 7 to 8 not in the fixtures. (Analyst session 2) Session 4, Oracle 11g: the same, 7 bytes at t_ts_exp_11g.dmp@0x22cc and @0x22d5, 11 bytes at @0x22a3; descriptor lengths 7, 11, 11 at @0x2288, 0x228c, 0x2290. (Analyst session 4) Session 17 (R-047): precisions 1 to 5, 7 and 8 added on 18c and 11g, both paths: the descriptor length is 11 for every f > 0 (`b4 00 0b 00` at tsp_exp_18c.dmp@0x22fb to 0x2313, = `truth_tsp.txt` data_length 11), the value is 7 bytes with a zero fraction (@0x231f, row 1) and 11 otherwise (@0x2364, row 2); stored fractions are rounded by the database (t4 `07 5c 75 e0` = 123,500,000 @0x23ec, truth_tsp.txt row 3). See docs/formats/exp.md section 6.4. (Analyst session 17)

H-014
- Statement: TIMESTAMP WITH TIME ZONE is 13 bytes in the datafile form, not 20. If the dump file holds 13 bytes, the layout is unknown (C-012). If it holds 20 bytes, the dump would use the OCI external form, which has the layout in C-011.
- Test: TSTZ column with a known value and a known offset such as +05:30; count bytes; compare the layout with C-011.
- Claims: C-009, C-011, C-012 (K-1)
- Result: the first branch holds for legacy EXP 18c, both paths: the dump holds 13 bytes, equal to DUMP(tstz,16). `0d 00 78 74 03 1a 0f 05 38 07 5b ca 00 19 5a` at t_tstz_exp_18c.dmp@0x22a6 (truth_tstz.txt row 1, +05:30); all 6 values equal the truth on both paths (tools/check_truth.py). The layout of the 13 bytes was not analysed (second-wave type; t_tstz was not in the fixture list of session 2). (Analyst session 2) Session 3 update: layout read from all 6 rows, both paths (docs/formats/exp.md section 6.5, tools/tstz_fields.py). Bytes 1-7: date and time in the DATE layout, in UTC, not local time: row 1 (19:34:55 +05:30) is `78 74 03 1a 0f 05 38` = 14:04:55 at t_tstz_exp_18c.dmp@0x22a8; row 3 (-08:00) is 2016-03-27 03:34:55 at @0x22d6. Bytes 8-11: nanoseconds, big-endian (`07 5b ca 00` = 123456000 at @0x22af); present even when zero (row 6, @0x2322), so the value is always 13 bytes. Bytes 12-13 for an offset zone: hour + 20, minute + 60: `19 5a` (+05:30) at @0x22b3, `14 3c` (+00:00) at @0x22ca, `0c 3c` (-08:00) at @0x22e1: confirmed for these three. For a region zone they are something else, with bit 0x80 of byte 12 set: `86 48` Europe/Moscow at @0x22f8, `d0 04` UTC at @0x230f, `81 90` America/New_York at @0x2326: unknown. This is not the 20-byte form of C-011. (Analyst session 3) Session 4, Oracle 11g: the same 13 bytes at the same offsets, including the region bytes: `86 48` at t_tstz_exp_11g.dmp@0x22f8, `d0 04` at @0x230f, `81 90` at @0x2326 (t_tstz_exp_11g.dmp is byte-identical to the 18c file from offset 0x2000 on; tools/tstz_fields.py). (Analyst session 4)

## RAW

(Analyst session 3) Session 4: the same on Oracle 11g (`04 00 00 ff 80 7f` at t_raw_exp_11g.dmp@0x224d; `d0 07` + 2000 bytes at @0x226a; all 7 rows equal truth_raw.txt of corpus/fixtures/11g on both paths). ## NULL

H-018
- Statement: A NULL in the middle of a row is shown with a length of zero and no data bytes. The dump file may use some other marker, so record exactly what appears for the NULL column.
- Test: row (1, NULL, 3) in a three-column table; compare to the truth rows.
- Claims: C-017, C-018, C-019
- Result: refuted for legacy EXP 18c ("length of zero" is wrong; "no data bytes" is right). A NULL VARCHAR2 column is the two bytes `fe ff` in the place of the length field, with no data bytes: middle NULL at t_frame_exp_18c.dmp@0x2295 and t_frame_exp_direct_18c.dmp@0x2293 (truth_frame.txt row 2), first-column NULL at t_frame_exp_18c.dmp@0x22b3 and t_frame_exp_direct_18c.dmp@0x22ab (row 5). `00 00` does occur, but after the last column of every row in the conventional file (t_frame_exp_18c.dmp@0x228d), not as a NULL. Tested with VARCHAR2 columns only; the row (1, NULL, 3) with NUMBER columns named in the test is not covered yet. Data Pump not examined. See docs/formats/exp.md section 5. (Analyst session 1) Session 2 update: the same holds for NUMBER and DATE columns and for all eight NULL patterns of t_nullmix, on both paths. Row (2, NULL, SSSS, date): `fe ff` in the place of the NUMBER at t_nullmix_exp_18c.dmp@0x22a9, t_nullmix_exp_direct_18c.dmp@0x22a7 (truth_nullmix.txt row 2); NULL DATE at t_nullmix_exp_18c.dmp@0x22f2 (row 5); NULL NUMBER at t_num_exp_18c.dmp@0x2451 (truth_num.txt row 33); NULL CHAR and NVARCHAR2 at t_text_exp_18c.dmp@0x238b, 0x238d. A length of zero was never seen in a field. See docs/formats/exp.md section 5.3. (Analyst session 2) Session 4, Oracle 11g: the same, `fe ff` at t_frame_exp_11g.dmp@0x2295 and t_nullmix_exp_11g.dmp@0x22a9; a row of six NULLs (VARCHAR2, CHAR, VARCHAR2, NVARCHAR2, VARCHAR2, DATE) at corpus/fixtures/11g-cp1251/ru_tbl_exp_cp1251_11g.dmp@0x4639-0x4644 (truth_ru.txt R_TEXT row 7). The marker can be cut by a record boundary: `fe` at t_bn3_exp_18c.dmp@0x3fff, `ff` at @0x4000 (same in t_bn3_exp_11g.dmp). (Analyst session 4) Session 7: a length of zero does not occur in any row field of the 169 EXP files (219,043 fields, 18,915 of them `fe ff`; tools/rowlen_stats.py, docs/formats/exp.md section 5.6); NULL is `fe ff` also for NCHAR, `CHAR(n CHAR)` and LONG (nchar_exp_18c.dmp@0x22e0, long_exp_18c.dmp@0x227e; the same offsets on 11g). (Analyst session 7) Session 8: a NULL LOB (CLOB, NCLOB, BLOB) is `fe ff` in its column too, and nothing of it follows the row (lob_exp_18c.dmp@0x2528, 0x252a, truth_lob.txt T_LOB row 2; lob_exp_11g.dmp@0x2526). An **empty** LOB (EMPTY_CLOB(), EMPTY_BLOB()) is not NULL: its column holds a locator, and after the row its value has the length 0 (`00 00` at lob_exp_18c.dmp@0x261c and @0x261e, truth_lob.txt `T_LOB|3|0|0`; @0x4dda5 for T_LOB2 row 2, `T_LOB2|2|NULL|y|0|NULL`; the same in lob_exp_11g.dmp@0x2602, 0x2604, 0x4e17c). So a length of zero does occur, but only in the LOB value area after a row, never in a column field (237,347 column fields of 177 files, tools/rowlen_stats.py). INTERVAL and ROWID NULLs are `fe ff` as well (misc_exp_18c.dmp@0x22f5, 0x22f7, 0x2497). See docs/formats/exp.md sections 5.6, 6.7, 14.6. (Analyst session 8) Session 9: NULL is `fe ff` also for a LONG column on the direct path (long_exp_direct_18c.dmp@0x227f, row 2 of T_LONG; @0x2280 on 11g), for a ROWID of an index-organised-table row (misc2_exp_<v>.dmp@0x254d) and for a VARCHAR2(10 BYTE) column next to character-semantics columns (t_probe11_exp_<v>.dmp@0x2755). Still no length 0 in any column field (238,657 fields of 199 files, tools/rowlen_stats.py). (Analyst session 9)

H-019
- Statement: Trailing NULL columns are not written at all in the datafile form. In the dump file they may either be missing or written as empty values. Check whether the column count in a record header equals the table column count or the count of non-trailing-null columns.
- Test: rows (1, NULL, NULL) and (1, 2, NULL) in a three-column table.
- Claims: C-017, C-019
- Result: confirmed in the variant "written" for legacy EXP 18c; the variant "missing" is refuted. Each trailing NULL is written as its own `fe ff`: row (GGGG, NULL, NULL) at t_frame_exp_18c.dmp@0x22a5 and @0x22a7, t_frame_exp_direct_18c.dmp@0x22a1 and @0x22a3 (truth_frame.txt row 3); row (NULL, HHHH, NULL) at t_frame_exp_18c.dmp@0x22bb, t_frame_exp_direct_18c.dmp@0x22b3 (row 5); all-NULL row at t_frame_exp_18c.dmp@0x22ab, t_frame_exp_direct_18c.dmp@0x22a5 (row 4). They are NULL markers, not empty values with length 0. No record header with a column count was found in either file; every row has 3 fields, equal to the table column count (`03 00` at t_frame_exp_18c.dmp@0x225d). The sentence about the datafile form cannot be tested with dump files. Data Pump not examined. See docs/formats/exp.md section 5. (Analyst session 1) Session 2 update: confirmed with typed columns. Trailing NULL DATE at t_nullmix_exp_18c.dmp@0x22f2 (truth_nullmix.txt row 5); two trailing NULLs at @0x230e, 0x2310 (row 7); three at @0x2318, 0x231a, 0x231c (row 8); direct path: t_nullmix_exp_direct_18c.dmp@0x22ea, @0x2302, @0x230a. (Analyst session 2) Session 4, Oracle 11g: the same, trailing `fe ff` markers at t_frame_exp_11g.dmp@0x22a5, 0x22a7 and t_nullmix_exp_11g.dmp@0x2318, 0x231a, 0x231c. (Analyst session 4)

H-020
- Statement: Column lengths of 250 bytes or fewer take 1 byte, and longer ones take 3 bytes in the datafile form. The dump file may use a different width. Test with a VARCHAR2 column holding 250 and 251 bytes.
- Test: rows with 250-byte and 251-byte strings; read the length field widths.
- Claims: C-017
- Result: refuted for legacy EXP 18c dump files, both paths: the width of the length field does not change. It is 2 bytes, little-endian, for every length. 250 is `fa 00` at t_len_exp_18c.dmp@0x277b, 251 is `fb 00` @0x287e, 254 is `fe 00` @0x2b8d, 255 is `ff 00` @0x2c94, 256 is `00 01` @0x2d9c, 257 is `01 01` @0x2ea5; t_len_exp_direct_18c.dmp@0x2765 (250), @0x2866 (251) (truth_len.txt rows 250 to 257). The sentence about the datafile form cannot be tested with dump files. See docs/formats/exp.md section 5.2. (Analyst session 2) Session 4, Oracle 11g: the same, `fa 00` at t_len_exp_11g.dmp@0x277b, `fb 00` @0x287e, `ff 00` @0x2c94, `00 01` @0x2d9c. In the text region the length of a field is the same u16 LE: `2e 01` (302) at own_exp_18c.dmp@0x2d5a and own_exp_11g.dmp@0x2d5f. (Analyst session 4) Session 8: the column field stays 2 bytes for every type of the fixtures, LOB locators included (lengths 102 to 1102). LOB data are written after the row and have a second form for long values: `fc ff`, the total length as 8 bytes little-endian, then chunks of `u16 length + bytes` (a CLOB of 200,000 bytes at lob_exp_18c.dmp@0x4358: `fc ff 40 0d 03 00 00 00 00 00`, then 12 chunks of 16,120 bytes and one of 6,560; 11g: 16,264 and 4,832 at lob_exp_11g.dmp@0x475a; truth_lob.txt `T_LOB|5|100000|100000`). Values up to 6,000 bytes have the ordinary 2-byte length (lob_exp_18c.dmp@0x270e `70 17`). See docs/formats/exp.md section 14.6. (Analyst session 8) Session 9: one exception to the fixed 2-byte length in column fields, on the direct path only: a LONG or LONG RAW value is written as a chain of pieces, each with a u16 LE length whose bit 0x8000 says that another piece follows. The 32,000-byte LONG of T_LONG is `9c 80` + 156 bytes, three times `19 9f` + 7961 bytes, `19 1f` + 7961 bytes at long_exp_direct_18c.dmp@0x2288, 0x2326, 0x4241, 0x615c, 0x8077 (11g one byte later); on the conventional path the same value is one field `00 7d` (long_exp_18c.dmp@0x2285). Short values on the direct path are one piece with the bit clear (`0a 00` + 10 bytes at long2_exp_direct_<v>.dmp@0x2274). LOB values: the short form `u16 n` is used up to exactly one chunk (16,120 bytes for a CLOB on 18c, 16,264 on 11g; lob3_exp_18c.dmp@0x84b3 `f8 3e`, lob3_exp_11g.dmp@0x1434d `88 3f`), the long form `fc ff` above it (lob3_exp_18c.dmp@0xe41b, 16,122 bytes; truth_lob3.txt rows 2, 3). See docs/formats/exp.md sections 6.6, 14.6. (Analyst session 9) Session 17 (R-040): a LONG on the conventional path keeps the 2-byte length up to 65,520 bytes, bit 0x8000 included (`00 80` at long3_exp_18c.dmp@0xa280, `f0 ff` @0x2228f; truth_long3.txt rows 2, 4); from 65,535 bytes it is `fd ff`, chunks `u16 n + n bytes` (4000 each) and `00 00` (@0x3228f, row 5); on the direct path a chain of any length (long3_exp_direct_18c.dmp@0x522fb, 100,000 bytes). ## Headers

H-021
- Statement: A legacy EXP file begins with the three bytes 0x03 0x00 0x01 and then the ASCII text "EXPORT:V" plus a version string.
- Test: read the first bytes of every EXP fixture.
- Claims: C-021
- Result: refuted as stated for legacy EXP 18c. The first three bytes are `03 03 69`, not `03 00 01` (t_frame_exp_18c.dmp@0x0000, t_frame_exp_direct_18c.dmp@0x0000). The text `EXPORT:V18.00.00` + LF is present, so that part holds, but it follows the three bytes directly only in the conventional file (t_frame_exp_18c.dmp@0x0003); in the direct-path file the two bytes `D` + LF come first and the text starts at t_frame_exp_direct_18c.dmp@0x0005. Only these two fixtures were read, not "every EXP fixture"; 11g not examined. See docs/formats/exp.md section 2. (Analyst session 1) Session 2 update: the lead is correct for a US7ASCII client and incomplete otherwise. Bytes 1-2 are the id of the client character set of the export session, big-endian: `03 00 01` at t_frame_exp_us7ascii_18c.dmp@0x0000 and t_frame_exp_direct_us7ascii_18c.dmp@0x0000 (US7ASCII = 1), `03 00 b2` at t_frame_exp_w1252_18c.dmp@0x0000 (WE8MSWIN1252 = 178), `03 03 69` at t_frame_exp_18c.dmp@0x0000 (AL32UTF8 = 873); ids from truth_charsets.txt, client set from the export logs. So the statement becomes: byte `03`, then a 2-byte character set id, then (direct path only) `D` LF, then `EXPORT:V`. All 38 EXP fixtures of 18c start this way. 11g not analysed. See docs/formats/exp.md section 2.1. (Analyst session 2) Session 4 update: the same on Oracle 11g with the text `EXPORT:V11.02.00`: `03 03 69` + `EXPORT:V11.02.00` at t_frame_exp_11g.dmp@0x0000 / @0x0003, `03 00 01` at t_frame_exp_us7ascii_11g.dmp@0x0000, `D` LF at t_frame_exp_direct_11g.dmp@0x0003; all 59 EXP files of corpus/fixtures/11g and all 15 of corpus/fixtures/11g-cp1251 start this way (`03 00 ab` with a CL8MSWIN1251 client at ru_tbl_exp_cp1251_11g.dmp@0x0000). Bytes 1-2 are the client set of the export; it is the character set of the statement text and identifiers in the file, not of the row data (docs/formats/exp.md section 14). (Analyst session 4)

## Other notes for the Analyst (not hypotheses)

The odv-testdump repository (C-023) has SQL scripts that could help build fixtures with all common types. It has no expected values, so truth files would still have to be made in a real database.

## Suggested order

1. H-021 and H-022 (headers), because they tell you which file is which and give the first working anchors.
2. H-018, H-019, H-007 (NULL and length framing), because every other value test depends on knowing where one value ends.
3. H-001, H-002, H-003, H-008 (NUMBER and DATE byte values). Documentation is consistent here, so these are the cheapest checks of whether dump files reuse the datafile form.
4. H-014, H-016, H-012, H-013 (timestamps), where the sources are thinnest.
